# regl-cli

The `regl` command line: it loads a schema file and a document — each a
filesystem path or an `http(s)` URL — decodes the document as JSON, YAML, or
`.properties`, validates it against the schema, and exits with a code a
pipeline or CI job can branch on.

```bash
regl <schema> <document>            validate a document against a schema file
regl validate <schema> <document>   the same, explicit
regl schema <schema>                load and lint a schema, print its fields
```

Built on [`regl-java`](../regl-java) (the zero-dependency validation core) and
specified by [`regl-spec/document-schema.md`](../regl-spec/document-schema.md)
§12–§14.

---

## Build

```bash
cd ../regl-java && mvn install      # once: publishes the core the CLI builds on
cd ../regl-cli && mvn package       # builds target/regl/bin/regl

target/regl/bin/regl --help
```

Requires JDK 17+. The launcher is generated by appassembler, so `bin/regl` and
`bin/regl.bat` work without an install step, like `bbrun`'s `installDist`.

## A schema

A schema is a file — JSON or YAML — in one shape:

```yaml
strict: true
maxDepth: 16
fields:
  server.port:                      # block style, what a hand author writes
    type: INTEGER
    rules: [notNull, { lessThan: 65536 }]
  servers.*.host: { type: STRING, rules: [notNull, email] }   # flow style, freely mixed
  tags:
    type: LIST
    rules:
      - notNull                     # a bare name: no argument
      - range!: { min: 1, max: 5 }  # a one-key map, `!`-marked — the count advises
      - unique                      # unmarked — duplicates fail the document
```

`strict` (default `false`) rejects unknown document keys; `maxDepth` (default
`32`) caps path length; `fields` is keyed by path and declares one chain per
path, in report order. `*` matches every element of a list, and `a\.b` keeps a
dot inside one key. A rule is its own name or a one-key map of
name to argument, in block or flow style, freely mixed; `!` on the name —
`maxLength!: 20`, or a bare `email!` — marks that one rule a warning, and
`severity: warn` on a field or type entry warns every rule it carries. `error`
is the default, a warning never fails a document, and the withdrawn
`{code, value, severity}` envelope is a load error. An unknown
key anywhere in a schema file is a **load error** — a typo must fail loudly, not
silently produce a schema that validates everything — and a repeated key is
one, since a repeated path is a duplicate path.

`regl schema <schema>` lints the file and prints what regl understood;
`regl schema --json <schema>` prints it normalized — the formal shape, one
`{path, type, rules}` entry per field, each rule `{code, value?, severity?}` —
which is the fastest way to see what a YAML schema really says.

## A document

The document is decoded by its format — `--format json|yaml|properties`
overrides detection, otherwise the file extension, otherwise the URL's
`Content-Type`:

| Format | Notes |
| :--- | :--- |
| JSON | Standard; the root may be any kind. |
| YAML | Full YAML — block and flow styles, anchors and aliases. A stream must hold exactly one document. |
| `.properties` | Dotted keys expand to nested objects (`server.port=8080` becomes `{server: {port: "8080"}}`), so a schema's paths address them directly. Every value is a string — no coercion (§8), so only `STRING` rules can pass. |

Nothing is ever coerced: a value whose kind contradicts the field's declared
type is a `TYPE_MISMATCH` finding, never a conversion.

## Exit codes

| Code | Meaning |
| :--- | :--- |
| 0 | The document is valid. Warnings may be present. |
| 1 | The document is invalid: at least one error-level finding. |
| 2 | Nothing was validated: a usage error, an unreadable or undecodable schema or document, an invalid schema. |

The distinction is for pipelines: 1 means "the document is wrong", 2 means
"regl could not do the job" — a CI step that regl itself failed to run should
not look like a red test.

## Output

Human output by default — one line per finding, errors before warnings, then a
summary (`ok`, or `N errors`):

```
$ regl schema.json app.yaml
ERROR server.port notNull: Value is required and must not be null.
ERROR servers.0.host email: Value is not a valid email address.
2 errors
$ echo $?
1
```

`--json` prints the machine-readable result — the shape the TypeScript CLI must
emit identically:

```json
{"valid": false,
 "errors": [{"severity": "ERROR", "kind": "RULE_FAILED", "path": "server.port",
             "rule": "notNull", "value": null,
             "message": "Value is required and must not be null."}],
 "warnings": []}
```

`--quiet` drops the summary — the exit code carries the verdict. `--no-color`
forces plain output; color is used only on a terminal anyway.

## Dependencies

The CLI may use proven libraries for what is not worth hand-rolling, exactly as
the validation core may not: `picocli` for argument parsing, `snakeyaml` for
YAML. `regl-java` — the validation core — stays zero-dependency, and holds the
JSON and `.properties` decoders itself.

## Testing

```bash
mvn test
```

The suite runs the shared decode fixtures
([`regl-spec/conformance/decode-cases.json`](../regl-spec/conformance/decode-cases.json))
for all three formats, checks that JSON and YAML spellings of one schema load
and validate identically, asserts every rejected schema of §12, and exercises
URL loading against the JDK's own HTTP server — so the remote path is tested
for real, without a dependency or a network.
